## 概要

`shared_store.py` のモジュールグローバルな状態が API リクエスト間で残留しうるため、前回実行のデータが次回実行に影響しないよう初期化方針と状態管理方式を見直す。

## 背景

現在の `shared_store` と `shared_canvas` はプロセス内のグローバルオブジェクトとして保持されている。一方で、`/reply` 実行時には `shared_store["user_id"]` を上書きするのみで、リクエスト開始時の明示的な初期化が行われていない。

評価スクリプトではケース間リークを避けるため `shared_store.clear()` による初期化を実施しているが、API 実行経路には同等の処理がない。そのため、以下のリスクがある。

- 前回リクエストの `profile` や `conversation` が次回実行時に残る
- 例外発生時や履歴未取得時に、古い `shared_canvas` の内容を返す可能性がある
- 並列リクエストや今後のワーカー構成変更時に、状態汚染の不具合が顕在化しやすい

## 要件

- `/reply` 実行開始時に `shared_store` と `shared_canvas` を安全に初期化する
- 初期化後も `self_profile` のデフォルト値は維持されるようにする
- 履歴取得失敗時や初回会話時でも、前回実行の `profile` / `conversation` / `generated_reply` などが残らないことを保証する
- 暫定対処に加えて、グローバル辞書ではなくリクエストスコープの状態オブジェクトへ移行する案を検討対象に含める

## 受け入れ条件

- [ ] `/reply` を連続で異なる `user_id` で呼び出しても、前回実行の `shared_store` / `shared_canvas` の内容が参照されない
- [ ] 履歴ファイルが存在しないケースやツール失敗時でも、レスポンスや後続処理に古いデータが混入しない
- [ ] API 実行経路で状態初期化が共通化され、評価スクリプトと同等のリーク防止が担保される
- [ ] 恒久策として、グローバル状態を廃止してリクエスト単位のコンテキストに置き換える場合の実装方針が整理されている

## 具体案（推奨）

- state は最小化し、分岐判断や監査に必要な値のみを保持する
- ツール間で共有したい作業データは request-scope の共通領域に保持する
- 共通領域は `execution_id` 単位でバケット分離し、リクエスト開始時に生成する
- ノードやツールには state 全体ではなく `execution_id` を渡し、必要時に共通領域へアクセスさせる
- API ハンドラの `finally` で `execution_id` バケットを必ず破棄し、例外時もリークしないようにする
- 可能なら TTL や最大保持件数のガードを設け、異常系での取り残しを回収する

## 第二案（最悪時の暫定対応）

- 構造変更がすぐに難しい場合は、`/reply` の入口で `shared_store` と `shared_canvas` を必ず初期化する運用を最低限の対策として採用する
