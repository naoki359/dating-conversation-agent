## 概要

`base_node` に集約しているログ出力処理と `logs/` 配下に保存される JSON ログの設計を見直し、特にツール実行結果を追跡できない課題を調査したうえで、改善方針を整理する。

## 背景

現在は各ノードの実行前後を `BaseNode.run()` で記録し、`json_logger` で `logs/<user_id>/<date>/` に JSON を保存している。一方で、`ActionNode` はツール実行後に `BaseToolResult` の内容をそのままログへ渡しておらず、永続ログにはノード要約しか残らない。

実装上は `BaseToolResult.data` にツール固有の結果を保持できるが、`ActionNode` の戻り値は `BaseOutputSchema` のため、`BaseNode._log()` に渡る時点で詳細結果が失われる。また、返信文など一部の成果物は state ではなく shared canvas に保存されており、`action_node` のログ出力タイミングでは `generated_reply` が `null` のままになるケースがある。

このため、以下の問題が起きている。

- どのツールが何を返したかをログから追えない
- 成功したツール実行でも、実ログ上は `node_data` が空のままになる
- ノードの要約ログと実際の成果物保存先が分かれており、障害解析や挙動確認に時間がかかる
- ログに残すべき情報と残しすぎない情報の境界が曖昧で、設計意図が不明瞭になっている

## 要件

- `base_node` 起点のログ出力責務と、各ノード・各ツールが持つべきログ責務を整理する
- `ActionNode` 実行時に、少なくともツール名、成功可否、要約、ツール固有の結果を追跡できるようにする
- shared store / shared canvas / ReactState のどこにある情報をログ対象にするかを棚卸しし、保存タイミングの妥当性を見直す
- `logs/` 配下の JSON について、運用上必要な最小単位で調査しやすいスキーマ案を作る
- 個人情報や冗長データの扱いも含め、ログ粒度とマスキング方針を整理する
- 調査の結果、`base_node` への集約を維持する案と、ツール実行ログを別イベントとして残す案の比較を行う

## 受け入れ条件

- [ ] 現行ログ実装の課題が、コード上の根拠と実ログ例をもとに整理されている
- [ ] ツール実行結果が失われる経路が特定され、再現条件と影響範囲が明文化されている
- [ ] 改善後に最低限残すべきログ項目が定義されている
- [ ] ログ保存の責務分担案が複数提示され、採用方針を判断できる状態になっている
- [ ] 必要であれば実装タスクへ分割できる粒度まで論点が整理されている

## 補足

- 初期調査対象の候補は `src/app/agent/core/nodes/base_node.py`、`src/app/agent/core/nodes/action/node.py`、`src/app/agent/core/utils/json_logger.py`、各 `tools/*/tool.py` とする
- 特に `BaseToolResult.data`、`ReactState.tool_result`、shared canvas の `generated_reply` / `reply_reasoning` が、どの時点でログに乗るべきかを確認する
- 実装着手前に、障害解析、評価実行、運用監視の各観点で「このログで何を確認したいか」を揃えておくと手戻りが少ない
