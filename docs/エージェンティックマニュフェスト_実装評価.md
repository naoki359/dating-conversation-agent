# エージェンティックマニュフェスト 実装評価

本ドキュメントは、[エージェンティックマニュフェストのお勉強.md](./エージェンティックマニュフェストのお勉強.md) の内容をもとに、現在の dating-conversation-agent の実装を評価したものである。

---

## ✅ よくできている部分

### 1. 観測可能性（Behavior Tracing）

マニュフェストが最重視する「log reasoning（意思決定過程のロギング）」が最もよく実装されている。

`src/app/agent/core/utils/json_logger.py` が各ノード実行ごとに `reasoning`・`thought_process`・`tool_calls` を含むJSONを書き出す設計は、**「責任の空白（Accountability Void）」への直接的な回答**となっている。

```
logs/{user_id}/{YYYYMMDD}/{trace_id}_{HHMMSS_μs}_{node_name}.json
```

各ログには以下が含まれる：
- `meta`：タイムスタンプ、user_id、trace_id、node_name、success
- `input`：プロフィール概要、直近N件の会話、状態サマリー
- `summary` / `reasoning` / `thought_process`：**意思決定の内部過程**
- `node_data` / `output` / `error`

### 2. ReActループ = 創発的な振る舞い

`DecisionNode` がどのツールを使うかをLLMに決めさせる設計は、**「事前定義されたロジックより創発的な振る舞いを重視する」** という価値観の体現である。

ハードコードされた分岐ではなく、状況に応じた行動選択（`GET_HISTORY` → `GENERATE_REPLY` → `CHECK_REPLY_PROFILE_FIT`）が可能になっている。

### 3. スペクトラム評価の萌芽

`CheckReplyProfileFitTool` が `fit_score`（0〜100）を返す設計は、PASS/FAILではなく**スペクトラム評価（ADLC Phase 3）** のアイデアを取り込んでいる。

| 評価要素 | 実装状況 |
|---|---|
| `fit_score`（0〜100） | ✅ 計算される |
| `reasons` | ✅ 出力される |
| `improvement_suggestions` | ✅ 出力される |
| `revised_reply` | ✅ 生成される |

### 4. 自己観察（Self-Awareness）

`DecisionNode` がループするたびに `state["history"]`（過去の思考プロセス）を読んで次の判断に活かす設計は、マニュフェストの以下の行動指針に対応している。

> あらゆる相互作用のたびに、システムは自身の有効性を振り返り、リアルタイムで自動的にアプローチを調整する。

## ❌ かけている部分

### 1. スコア駆動の自己修正ループ（最も大きなギャップ）

`CheckReplyProfileFitTool` が返す `fit_score` と `revised_reply` は現在誰にも読まれていない。

```
現状：       generate_reply → check_reply → (スコアを無視) → END
あるべき姿：  generate_reply → check_reply → fit_score < 閾値？ → generate_reply へ戻る
```

評価が「観測で終わっている」状態であり、**ADLC Phase 3「継続的なチューニング」の実装が途中**となっている。

### 2. ガードレール（ADLC Phase 1）がない

| 設計すべき要素 | 実装状況 |
|---|---|
| 目標（Goal） | ❌ |
| 禁止事項（Guardrails） | ❌ |
| 評価指標（KPI） | ❌ |
| 倫理制約 | ❌ |
| 人間介入ルール | ❌ |

エージェントが「どこまでやっていいか」を自分で判断する手がかりがない状態。

### 3. Human-on-the-Loop がない

グラフに `interrupt()` が一切なく、4ループで強制終了するだけである。マニュフェストが求める以下の考え方が実装されていない。

> 人間は介入者ではなく監督者として関与する（Human-on-the-Loop：必要時のみ介入する監視型の関与）

### 4. 明示的な終了信号がない（行動の経済性に反する）

ループの終了がカウンタ上限（4回）のみで決まっている。「目標を達成した」とLLM自身が判断して終了するシグナルがなく、以下の行動指針に反している。

> 行動の経済性（Economy of Action）――最小限の計算負荷と認知負荷で最大の目標を達成すること――は、スケーラブルな自律性に不可欠である。

### 5. マルチエージェント構成がない

単一エージェントのみで、「**エージェントの社会として構築する**」という行動指針は未着手である。

※ ただしこれはマニュフェスト自身が「複雑さは指数的に増加する」と述べており、後回しにすることは合理的な判断である。

### 6. APIのバグ

`POST /reply` が `generated_reply` を常に `""` で返している。`shared_canvas["generated_reply"]` が API レスポンスに含まれておらず、**動くソフトウェアを提供するという基本原則に反している**。

## 優先度まとめ

| 優先度 | 内容 | 対応するマニュフェストの概念 |
|--------|------|------------------------------|
| 🔴 高 | APIの `generated_reply` バグ修正 | 動くソフトウェアが進捗の主要指標 |
| 🔴 高 | `fit_score` による再生成ループの実装 | 継続的なチューニング（ADLC Phase 3） |
| 🟡 中 | 明示的な終了信号の実装（LLMによる `is_done` 判断） | 行動の経済性 |
| 🟡 中 | ガードレール設計（目標・禁止事項・KPI） | ADLC Phase 1 |
| 🟢 低 | Human-on-the-Loop の実装 | 監督者としての人間 |
| 🟢 低 | マルチエージェント化 | エージェントの社会 |

## ADLC フェーズ別の実装状況

| フェーズ | 内容 | 実装状況 |
|---|---|---|
| Phase 1: 構想とガードレール | 目標・禁止事項・KPI設計 | ❌ 未着手 |
| Phase 2: 開発と能力付与 | プロンプト設計・ツール接続 | ✅ 実装済み |
| Phase 3: 妥当性評価とロバスト性 | スペクトラム評価・自己修正ループ | ⚠️ 途中（スコア計算はあるが活用されていない） |
| Phase 4: デプロイとリリース | 段階的ロールアウト・振る舞いの監視 | ❌ 未着手 |
| Phase 5: 監視とチューニング | 本番ログ監視・改善ループ | ⚠️ ログ基盤はあるが継続改善の仕組みがない |
