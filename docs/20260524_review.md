## 1. アーキテクチャ概要

```
[FastAPI: entrypoint.py]
  └─ POST /reply
      ├─ UUID発行 → create_execution_bucket()
      ├─ build_graph()（ReActまたはFixedを選択）
      └─ graph.invoke() → get_shared_canvas() → ReplyResponse

   [LangGraph ワークフロー]
    FixedPipeline: GetHistoryAndFacts → GenerateReplyCandidates
      → EvaluateReplyCandidates → RefineReplyCandidates → ...

    ReActLoop: Decision → Action → Observe →(continue)→ Decision
                                           →(end)→ CreateAnalysisLog → END

   [共有メモリ: shared_store.py]
      _ExecutionBucket: { store(SourceData), canvas(Canvas) }
```

**State/Canvas分離**、**BaseNode継承パターン**、**実行バケット機構**という設計の核心は洗練されています。

---

## 2. 良い点

1. **ReactState / Canvas の明確な責務分離** — `state.py` の設計意図が明快
2. **BaseNode テンプレートメソッド** — ロギング・エラーハンドリング・キャンバス更新の共通化で実装漏れを防止
3. **実行バケットのスレッドセーフ設計** — `_bucket_lock`・TTL・最大バケット数制限が整備されている
4. **プロンプトの完全外部化** — `prompt.yaml` でプロンプトエンジニアリングとコードが分離
5. **パイプラインモード切り替え** — `AGENT_PIPELINE_MODE` による ReAct/Fixed の柔軟な切り替え
6. **Settings の起動時バリデーション** — `validate()` で不正設定を早期検出

---

## 3. 問題点・改善提案

### 🔴 Critical

**C-1: `ToolEnum` — ツールがアプリ起動時にシングルトンで生成される**  
tool_enum.py  
`ToolEnum` 評価時点で全ツールがインスタンス化され、並行リクエストが同一インスタンスを共有する。内部状態が混在するリスクがある。  
→ ファクトリー関数パターンに変更するか、リクエストごとにインスタンス化する。

**C-2: `ActionNode.execute()` 内での `state` 直接変更（LangGraph 設計違反）**  
node.py  
```python
state["observation_flg"] = True  # execute()内での直接変更
```
LangGraph のイミュータビリティ前提を破る。`update_state()` で更新すべき。

**C-3: `FinalReplyRewriteNode._last_execution_id` インスタンス変数が並行リクエスト時に危険**  
node.py  
シングルトン的に生成されたノードが並行リクエスト間で `_last_execution_id` を上書きし合う恐れ。  
→ `execution_id` はインスタンス変数ではなくメソッド引数として渡す設計に変更。

**C-4: パストラバーサルの脆弱性**  
yaml_user_repository.py  
```python
return Settings.get_data_dir() / f"{user_id}.yaml"  # user_id 未検証
```
`user_id` に `../../etc/passwd` を渡すと data 外のファイルが読める。  
→ `ReplyRequest` に正規表現バリデーションを追加:
```python
id: str = Field(..., pattern=r'^[a-zA-Z0-9_\-]+$')
```

**C-5: `BaseNode.run()` のエラー状態がグラフに反映されない**  
base_node.py  
例外発生時に `error_state` を構築してログに記録するが、直後に `raise` するためグラフには渡らない。

---

### 🟠 Major

**M-1: 無効な `execution_id` で暗黙的に空バケットを生成する**  
shared_store.py  
→ バケット未存在時は `KeyError` を送出すべき。

**M-2: `entrypoint.py` で例外時の HTTP エラーレスポンスが欠如**  
内部情報がクライアントに漏洩する可能性。`HTTPException` で適切なメッセージを返す。

**M-3: `get_graph()` がリクエストごとにグラフを再構築**  
コメントアウトされた `@lru_cache(maxsize=1)` が無効化されており、全ノード・全ツールが毎回再インスタンス化される。

**M-4: `generate_reply_candidates` の LLM 呼び出しが直列4回**  
4テーマが独立しているのに順次実行。`asyncio.gather()` で並列化すると約4倍の速度改善が期待できる。

**M-5: `Settings.validate()` がモジュールインポート時に実行される**  
llm_client.py  
テスト環境で `OPENAI_API_KEY` 未設定時にインポートが失敗し、テスト不可能。

**M-6: `shared_store.py` が God Module（600行超）**  
TypedDict 定義とバケット管理ロジックが混在。TypedDict は `schemas/` に分離すべき。

**M-7: `mlflow.set_tracking_uri` がハードコード**  
entrypoint.py  
`"http://127.0.0.1:5000/"` を `Settings` の環境変数に移す。

**M-8: `FinalizeReplyNode` がデッドコード**  
node.py は実装があるがグラフに組み込まれていない。

---

### 🟡 Minor

| | 箇所 | 内容 |
|---|---|---|
| mn-1 | `base_node.py` | `state.copy()` が浅いコピー → `copy.deepcopy()` を使う |
| mn-2 | `build_graph.py` 他 | コメントアウトされたコードが大量残存 |
| mn-3 | 各所 | `print` の多用 → `logging` モジュールに統一 |
| mn-4 | main.py | `print("Hello...")` のみで実質空 |
| mn-5 | `formatCommon.py` | PEP 8 違反のファイル名 → `format_common.py` |
| mn-6 | 各所 | `observation_flg` → `observation_flag` に統一 |

## 4. セキュリティ

| 項目 | 深刻度 | 詳細 |

| 入力バリデーション不足 | 🟠中 | `ReplyRequest.id` に文字種制限なし |

## 5. テスト

**現状**: テストは test_trigger_text.py の1ファイルのみ。ノード・ツール・リポジトリ・グラフ・エンドポイントのテストがゼロ。

主な問題:
- LLMを直接 `__init__` で呼ぶため DI が不十分でモック不可能
- eval スクリプトが手動実行前提で CI 未組み込み
- `dev` 依存に `pytest-mock`, `pytest-asyncio`, `httpx` が欠如
