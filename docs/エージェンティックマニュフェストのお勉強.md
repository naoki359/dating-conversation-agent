# エージェンティックマニュフェスト

## 🟩 概要

本ドキュメントは、「エージェンティックマニュフェスト」の内容をもとに、自身の理解を整理したメモである。従来のソフトウェア開発とは異なる、エージェント型システムにおける考え方や開発・運用のあり方について、価値観・行動指針・問題提起・ライフサイクルの観点からまとめている。なお、本内容は以下のブログを参考にしている。

[The Agentic Manifesto: Engineering in the Era of Autonomy](https://caseywest.com/the-agentic-manifesto/?utm_source=chatgpt.com#the-multi-agent-exponential)

## 🟦 価値観

- 「事前に定義されたロジックよりも、**創発的な振る舞い**を重視する」
- 「固定された要件よりも、**動的な目標**と**ガードレール**を重視する」
- 「合否判定のテストよりも、**継続的なチューニング**を重視する」
- 「手動管理よりも、**自動化されたガバナンス**を重視する」

## ⬜ 行動指針

※ アジャイルの12の原則と同一の内容には✅をつけています

- 価値あるソフトウェアを継続的に提供し顧客満足を実現する(✅)
- 開発の後半でも要件変更を歓迎する(✅)
- 動くソフトウェアを頻繁に提供する(✅)
- ビジネス側と開発者が日々協力する(✅)
- システムは単一のエージェントではなく、エージェントの社会として構築する。私たちは個々の行動だけでなく、これらのデジタル組織における相互作用や創発する文化を統治する。
- エージェントに意図を伝える最も効率的な方法は自然言語であり、エージェントからの最も有効な出力は観測可能な行動である。
- 動くソフトウェアが進捗の主要指標(✅)
- 人間は介入者ではなく監督者として関与する（Human-on-the-Loop：必要時のみ介入する監視型の関与）
- 行動の安全性と倫理的整合性に継続的に注意を払うことが、エージェントの自律性を高めることへつながる。
- 行動の経済性（Economy of Action）――
最小限の計算負荷と認知負荷で最大の目標を達成すること――は、
スケーラブルな自律性に不可欠である。
- 最良のアーキテクチャは作り込むものではなく、育てるものである。
私たちは、エージェント同士の相互作用から有効な解決策が創発するように、
制約やインセンティブを設計する。
- あらゆる相互作用のたびに、
システムは自身の有効性を振り返り、
リアルタイムで自動的にアプローチを調整する。

## 🟨 問題提起

1. 従来のソフトウェア開発の前提
   1. ロジックを書く → 結果は制御可能
2. Agentic AI（指示された処理を実行するAIではなく、目標をもとに自律的に行動・計画するAI）の特徴 
   1. 設計上 非決定的（non-deterministic）
      1. 目標解釈
      2. 計画生成
      3. 創発行動
      4. 非決定性
3. 21世紀の存在（AIエージェント）を20世紀のツールで管理しようとしていた
   1. AIを利用することでコーディング速度は上がったが、デリバリー速度（ユーザーへ価値を届けるまでの時間）は改善されなかった、もしくは低下した可能性がある
   2. 非効率なだけでなく危険でもあるらしい
   3. 根拠？ → [DORA State of DevOps Report 2024](https://dora.dev/research/)
4. SDLC(Software Delivery Lifecycle)からADLC(Agentic Delivery Lifecycle)への転換が必要
   1. ADLC = 「不確実性を排除するのではなく、受け入れる新しい運用モデル」

## 🟥 決定性ギャップ（Determinism Gap）とは？

「結果が事前に決まるソフトウェア」と「実行の過程で結果が生まれるエージェント」の本質的な違いを表している単語と理解した
```
従来のソフトウェアとエージェント型システムの間に存在する深い隔たりを、
私たちは 「決定性ギャップ（Determinism Gap）」 と呼ぶ。

これは、出力が事前に分かっているシステム と
出力がリアルタイムで発見されるシステム

の違いである。

このギャップにより、
私たちが長年信頼してきた 従来のソフトウェア工学の実践 は、
もはや十分ではなくなっている。
```
### 1️⃣ バイナリテストの限界（The Failure of Binary Testing）

1. 従来のソフトウェアのテスト PASS / FAIL → **仕様通りに動くかを確認**
2. Agentic Systemの評価が下記のように複数軸になるになる → スペクトラム評価(良い ←--------→ 悪い)
   1. 品質
   2. コスト
   3. 効率
   4. トーン
   5. 安全性
3. テスト思想の変化
   1. Verification ⇔ Validation
   2. 「言った通りに動いたか」　⇔ 「本当に望んだ結果になったか」


#### **✔️ まとめ**

⇒ **Agentic AI は PASS / FAIL のテストでは評価できない**

- 評価
- スコアリング
- 継続的改善

これらが必要となってくる

### 2️⃣ リグレッションの不可視性（The Invisibility of Regression）

1. 従来のソフトウェアではコード変更の影響範囲を追跡可能
   1. git diff
   2. unit test
2. Agentic System追跡コスト増大 
   1. システムのふるまいレベルで変更がかかってしまう
      1. プロンプト変更
      2. RAGへのドキュメント追加
      3. モデル更新
3. コード変更ではないので、現在運用中であるCI、レビュー、テストで検知がしづらい

#### **✔️ まとめ**

⇒ **Agentic AIでは「振る舞いの変更」がコード変更なしに発生する**

```md
従来
出力 = 1つ
↓
回帰テスト可能
↓
CIが機能

Agentic
出力 = 複数
↓
回帰テストが難しい
↓
CIが弱くなる
```

且つ、ふるまいレベルで挙動が変わるため、影響範囲の特定や原因の特定が非常に難しくなる

```md
System =
Code
+ Prompt
+ Knowledge
+ Model
+ Tools
```
システムを構成する要素がコードだけじゃなくなったから大変だよねというお話

### 3️⃣ 責任の空白（The Accountability Void）

1. DevOpsが提供したもの ⇒ コードの可観測性（何が起きたかを追跡できること）
   1. ログ
   2. メトリクス
   3. トレース
2. Agenticシステムの問題
   1. 行動の判断が見えない
3. 問題の例
```
もしエージェントが

間違った送金
誤った顧客対応
誤った医療助言

をしたとき

原因：LLM hallucination

では

企業では許されない。
```
4. 必要なものはAgentOps（AI意思決定の可観測性）

#### **✔️ まとめ**

⇒ AIの「行動」だけでなく「意思決定過程」を観測できる仕組みが必要

- 🙅‍♂️ log code
- 🙆‍♂️ log reasoning

### 4️⃣ マルチエージェントによる指数的複雑化（The Multi-Agent Exponential）

単一エージェントからマルチエージェントシステム（MAS: Multi-Agent Systems）へ移行すると、

複雑さは 線形的に増えるのではなく指数的に増加する。

1. 単一エージェント（Agent → Action → Result）⇒ 比較的に単純
2. マルチエージェント（Agent A ↔ Agent B ↔ Agent C）⇒ 複雑

#### 新しい障害

1. フィードバックループ
   1. Agent A → Agent B → Agent A → Agent B
   2. エージェント間の無限ループが発生する
2. リソース競合
   1. Agent A → GPU要求
   2. Agent B → GPU要求
3. 目標衝突
   1. Agent A → コスト最小化
   2. Agent B → 品質最大化

#### 従来の監視ツール
従来のAPMは
- CPU
- Memory
- Latency

Agentに対しては
- Reasoning：「なぜそう考えたかの内部思考」
- Dialogue：「他者（人 or エージェント）とのやり取り」
- Decision：「最終的に選択された行動」

#### 必要なもの

必要なのは
```
Behavior tracing
(「エージェントがどのような行動を取り、どんな経路で意思決定に至ったかを記録・可視化すること」)
```

つまり
```
Agent reasoning：エージェントの推論（思考プロセス）→ 内部で「どう考えたか」
Tool calls：ツール呼び出し（外部機能の実行）→ 実際に「何を実行したか」
Agent conversation：エージェント間の対話→ 他のエージェントと「どうやり取りしたか」
```
が重要となってくる

## ⬜ SDLC vs ADLC 比較

| 項目 | 従来のSDLC（決定的） | ADLC（エージェント型） |
|------|----------------------|--------------------------|
| 中心単位 | コード / 機能 | 振る舞い / 目標 |
| 主な目的 | 機能性（正しく動作するか？） | 目標達成（効果的に達成できるか？） |
| システムの性質 | 決定的（予測可能） | 非決定的（創発的） |
| 主な活動 | コーディング / 実装 | チューニング / 最適化 |
| 計画の焦点 | 固定された要件 | 目標とガードレール |
| テストの焦点 | 検証（Pass / Fail） | 妥当性評価（質的評価・ロバスト性） |
| 主要成果物 | 実行可能バイナリ / コンテナ | バージョン管理されたエージェント（プロンプト・ツール・モデル） |
| 主なリスク | ロジックバグ / スコープ肥大 | 創発的挙動 / 予測不能な行動 |

※ ロバスト性とは環境や条件が変わっても、安定して正しく動き続ける性質

ロバストなシステム

```
入力: 「東京の天気」
入力: 「東京　天気」
入力: 「今日の東京の天気教えて」
```

👉 全部ちゃんと理解して答える

## 🟩 Agentic Delivery Lifecycle (ADLC)とは

自律的に動くAIを、継続的に監視・評価しながら改善し続けるための運用・開発モデル

エンジニアリングの焦点を

- 静的なコードから動的な振る舞いへ
- 固定された要件から柔軟な目標へ
- 二値的なテスト（Pass / Fail）からリアルタイムの監視へ

と移行させる。

ADLCは、従来のエンジニアリング原則を否定するものではなく、
それらを進化させたものである。

SDLC（ソフトウェア開発ライフサイクル）を置き換えるのではなく、
それを包み込む（wrapする）存在である。

### 🚫 Phase 1: 構想とガードレール（Ideation & Guardrails）

✅ **要件から境界へ**

1. 従来との違い
- 従来：要件を細かく決める
- ADLC：やっていい範囲・ダメな範囲を決める

2. 設計の考え方
- 🙅‍♂️ 作り方を決める
- 🙆‍♂️ ルールと目的を決める

3. 設計するもの
- 目標（Goal）
- 禁止事項（Guardrails）
- 評価指標（KPI）
- 倫理制約
- 人間介入ルール

### 🔨 Phase 2: 開発と能力付与(Development & Empowerment)

✅ **ロジックのコーディングから、意図のエンジニアリングへ**

エージェントのすべての行動をプログラムするのではなく、エージェント自身が行動を計画できるように“装備させる”

- 基本原則の設計から、メタプロンプトの技術に至るまでの緻密なプロンプトエンジニアリング
（例：「Unlock Elite Agents: The Art of Evolving LLM Prompts into System Masterpieces」で詳述されている）
- 知識ベースの整備（例：RAG）
- エージェントが利用するツール（例：API）の安全な統合


1. 従来との違い
- 従来：ロジックを書く
- ADLC：意図と環境を設計する

2. やること
- プロンプト設計
- 知識（RAG）整備
- ツール（API）接続

3. 本質
- 🙅‍♂️ 行動を決める
- 🙆‍♂️ 行動できる能力を与える

➡️ 「どう動くかを書く」のではなく、「自分で考えて動けるようにする」フェーズ

### 📝 Phase 3: 妥当性評価とロバスト性(Validation & Robustness)

✅ **テストカバレッジから、振る舞い評価へ**

単純なコードカバレッジ指標を、「よく設計された評価スイート（Well-Curated Evaluation Suite）」 に置き換える。

評価スイート（Well-Curated Evaluation Suite）は
- 大規模で
- バージョン管理され
- 多様なシナリオ
- 敵対的プロンプト（レッドチーミング）
- 質的評価のためのスコアリング基準

から構成される

1. 転換のポイント
- 従来：テストカバレッジ（網羅率）
- ADLC：振る舞い評価（Evaluation）

1. 評価の方法
- シナリオベース
- レッドチーミング
- スコア評価

1. 何を評価するか
- 🙅‍♂️ 文字一致
- 🙆‍♂️ 意味・意図

➡️ 「正解かどうか」ではなく「どれだけ良い振る舞いか」を測るフェーズ

### 💻 Phase 4: デプロイとリリース(Deployment & Release)

✅ **一斉リリースから、段階的導入へ**

1. 転換のポイント
- 従来：一斉リリース
- ADLC：段階的リリース

2. やること
- カナリアリリース（新しいバージョンのシステムを一部のユーザーだけに先に公開して、安全性を確認するリリース手法）
- 段階的ロールアウト
- 振る舞いの監視

3. なぜ必要か
- エージェントは非決定的であり、本番でしか分からない挙動があるため

4. 見るべきもの
- 成功率
- 不快率
- エラー行動
- 逸脱行動

### 📈 Phase 5: 監視とチューニング〈アウターループ〉（Monitoring & Tuning）

✅ **コストセンターから、価値創出エンジンへ**

従来のソフトウェアでは、「保守（maintenance）」はコストセンターと見なされてきた。

私たちは本番環境でのインタラクションを継続的に監視し、
**効果の高いチューニング機会（high-leverage tuning）**を特定する。

例えば、

- ハルシネーションを1つ修正する
- 目標達成の精度を少し改善する

これらはすべて、
デジタル従業員（エージェント）の価値を直接向上させる。

このシステムは決して「完成」しない。

継続的に価値が増していく資産（appreciating asset）なのである。

1. 転換のポイント
- 従来：保守 = コスト
- ADLC：改善 = 価値創出

2. やること
- 本番ログの監視
- 評価データ収集
- チューニング
- 改善ループ

3. 本質
- 🙅‍♂️ 作って終わり
- 🙆‍♂️ 運用で価値を増やす

4. 重要な考え方
- エージェント = デジタル従業員

👉 運用しながら改善し続けることで、AIの価値を増やし続ける

✅ AIはプロダクトではなく「成長する資産」
